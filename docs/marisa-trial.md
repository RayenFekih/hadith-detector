# Prebuilt MARISA v2 trial and acceptance report

Historical snapshot: the maintainer subsequently accepted the initialization costs
and approved adoption. See [the production integration](marisa-production.md) for
current status; the measurements and trial-stage statements below retain their context.

Measured on 2026-10-14 before Phase 5. **Production adoption is pending review.**
The installed library still uses format v1 and RapidFuzz as its only runtime
requirement. No production code, dependency group, lockfile, or existing index was
changed. Phase 5 remains unstarted; no commits, pushes, or releases were made.

## Implemented trial

Repository-only `tools.marisa_trial` builds and loads prebuilt format-v2 resources.
It replaces the normalized-word-to-ID dictionary and trigram-to-posting-block
dictionary with two heap-loaded `RecordTrie("<I")` resources. Vocabulary IDs retain
first-occurrence order; trigram block IDs retain sorted-triple order. Each trigram
key is three concatenated eight-digit lowercase hexadecimal vocabulary IDs.
The tries store the existing IDs explicitly, never MARISA's autogenerated IDs.

Original records, record identity lookup, source spans/segments, posting arrays,
posting directories, exact/fuzzy verification, ranking, alignment models and caches
retain their existing representations and behavior. The trial initializes fuzzy
inverse vocabulary and length buckets in vocabulary-ID order. Its process-local
loader substitution is benchmark wiring, not a proposed public backend option.

The offline builder pins MARISA 1.4.1 and records native construction settings,
Python/Unicode versions, code fingerprints, project lock fingerprint and the
separate benchmark requirements fingerprint. Binary headers identify v2; remaining
binary payloads and file-kind identifiers are unchanged. Record, token, manifest
and normalization versions remain 1. Native resources replace `vocabulary.json`
and `trigram-keys.bin`; no legacy dictionaries are constructed during v2 loading.

Loading checks every artifact checksum before native parsing, then checks complete
unique ID coverage, unique native mappings, trigram encoding/order, source records,
token spans/segments, posting bounds/order and complete occurrence inventories.
Trigram keys are recovered into a temporary compact array by stored block ID for
posting validation. That array is released after loading. Native parser errors are
reported as invalid resources. The builder validates in a staging directory before
renaming, refuses overwrites and removes failed staging outputs.

## Measurements and acceptance

Windows 11 build 26200, CPython 3.14.6, Intel64 Family 6 Model 183 Stepping 1;
RapidFuzz 3.14.6 and MARISA 1.4.1. Three fresh-process pairs ran sequentially in
baseline/native, native/baseline, baseline/native order. Each of 39 representative
queries had one cache-cold call and three warm repetitions. No other tests or
full-corpus validation ran during timing. OS disk caches were not flushed.

The original v1 directories were unreadable in this session. A separate offline
rebuild with the unchanged production builder reproduced the original manifest
SHA-256 exactly, so the comparison uses the original v1 artifact bytes. Original
directories and prepared/source data remain untouched.

Memory savings and median detection latency do not automatically accept them.
The acceptance summary explicitly flags initialization and never adopts production
changes automatically. First-call costs are separately reported for human review.

## Correctness, reproducibility and compatibility

- All 168 saved fuzzy and 168 exact full-corpus oracle expectations passed offline.
  Every timed repetition also matched the representative oracle expectations,
  including complete references, source occurrences, costs and canonical traces.
- Two full-corpus builds are byte-identical, including manifests, and both pass
  offline structural/integrity verification. Counts remain 14,940 records,
  1,039,600 tokens, 40,949 vocabulary entries, 382,866 trigram keys and
  1,009,649 trigram occurrences.
- Eleven final synthetic tests passed on Windows and Linux/WSL using Python
  3.11–3.14. They cover preserved IDs/binary payloads, duplicate mappings, invalid
  IDs/encoding, checksum failure, native truncation, v1 rebuild instructions,
  failed-build cleanup, duplicate narrations, barriers, symbols and independent
  exact/fuzzy oracle agreement.
- The same Windows-prebuilt resources load and perform exact/fuzzy matching offline
  on Linux Python 3.11–3.14 and Windows Python 3.14. Network sockets are forbidden
  in timed workers, the full oracle comparison and compatibility probes.
- Existing quality and packaging checks pass: 125 existing tests, Ruff lint/format
  and strict mypy for the unchanged package. The two isolated-library test modules
  are intentionally skipped in the normal environment; MARISA tests run separately.
  Installed metadata still declares RapidFuzz only, and resource bundling remains absent.

Cross-platform reading is demonstrated on x86-64 Windows/Linux; byte-identical
construction across different platforms is not assumed. The existing survey found
approximately 0.41 MiB installed Windows MARISA files, native imports across the
retained Python matrix and no mandatory Python transitive dependencies. Production
dependency installation/clean-wheel v2 tests belong to adoption after review.

## Reproduction, decision and rollback

Use an isolated environment with `tools/library_benchmark/requirements.txt`, the
current library, pytest and the existing data preparation dependencies. The normal
project dependency groups intentionally do not yet contain MARISA. Run from the
repository root with Python 3.14; choose new output directories:

```text
python -m tools.marisa_trial.build --corpus-dir data/prepared-corpus --output-dir data/marisa-v2-a
python -m tools.marisa_trial.build --corpus-dir data/prepared-corpus --output-dir data/marisa-v2-b
python -m tools.build_index --corpus-dir data/prepared-corpus --output-dir data/marisa-baseline
python -m tools.marisa_trial.benchmark run --baseline data/marisa-baseline --trial data/marisa-v2-a --suite data/library-evaluation-final/suite.json --output data/marisa-acceptance-measured
python -m tools.marisa_trial.report data/marisa-acceptance-measured
python -m tools.marisa_trial.benchmark parity --trial data/marisa-v2-a --evidence data/phase4-final --report data/marisa-acceptance-measured/full-parity.json
python -m tools.marisa_trial.compatibility --index data/marisa-v2-a --report data/marisa-compat.json
python -m pytest tests/test_marisa_trial.py
```

Generated resources, six raw performance reports, logs, summary, full-parity report
and compatibility reports remain ignored. The representative suite and full oracle
evidence come from the previously documented Phase 3/4 evaluation workflows.

**Recommendation:** retain the production v1 loader until the maintainer reviews the
initialization/first-call costs. The memory benefit justifies continuing with the
minimal architecture. Prefer investigating stream-validation overhead before
adoption; accepting the measured one-time cost is also a concrete review option.
No memory reduction or warm-call result overrides that gate.

After acceptance, promote the concrete lookups/loader into the private package,
require MARISA 1.4.1, retain v2 only and add clean-wheel/CI coverage. Reject v1 with
an explicit offline rebuild instruction. Rebuild into new directories; never
overwrite preserved v1 resources. Roll back through the previous library and its
preserved v1 directory. There is no alternate runtime backend or automatic conversion.
